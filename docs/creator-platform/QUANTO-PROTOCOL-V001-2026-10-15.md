## Purpose

Establish the smallest truthful and mechanically testable basis for a future ANEVUM economic system without confusing a proposed currency with real money. The name QUANTO / QTO is provisional pending clearance. This module is not part of RHEN's separate Lab research account, wallet, broker connection, or currency simulation.

## In-scope software

- A browser-memory-only public demonstration page using the existing cinematic Continuance design language.
- Three purely fictional sample participants (Origin, Creator and Studio); none are linked to actual members.
- Pure JavaScript double-entry ledger with integer-cent units. No floating-point posting.
- Three atomic instruction types: issue, transfer, redeem.
- Explicit preview/review and confirmation on every transaction.
- Strict positive bounded amount, fixed wallet list, limited instruction schema, nonnegative demo balances and duplicate-request-ID rejection.
- Separate fictional QTO and SIM_USD posting accounts. Issue adds equal fictional backing and circulation; redemption subtracts both.
- 500-entry maximum per browser session; 1,000,000 cents per instruction; 100,000,000 cents maximum outstanding.
- A read-only 24-entry journal preview and full local JSON export.
- A local JSON verifier that replays commands from a zero-balance ledger and requires exact journal and balance consistency. It cannot establish real-world authenticity.
- One additive, clearly marked link from the verified member overview into the standalone unconnected demo. No account entitlements or balances are joined.

## Ledger mechanics

Accounts: QTO.{issuer,operator,creator,studio} and SIM_USD.{reserves,source}.

**Issue 2500 cents to creator:**
- QTO.issuer -2500, QTO.creator +2500.
- SIM_USD.reserves +2500, SIM_USD.source -2500.

**Transfer 1000 cents, creator to studio:**
- QTO.creator -1000, QTO.studio +1000.
- No change to SIM_USD.

**Redeem 1000 cents from studio:**
- QTO.studio -1000, QTO.issuer +1000.
- SIM_USD.reserves -1000, SIM_USD.source +1000.

For every entry and denomination, the postings sum to zero. Total non-issuer QTO equals fictional reserves. Debits must be funded before acceptance. Invalid instructions leave the old state untouched. Identical request-ID retries return the existing state, and conflicting retries fail.

**Crucial limitation:** Fictional reserve postings are generated by the same code that issues QTO. They prove accounting arithmetic only, not possession of one dollar, regulatory backing, solvency, independent audit, ability to redeem or legal monetary value. A self-consistent fabricated JSON can pass replay verification. The export is not signed and is not an external attestation.

## Explicit non-features

1. No USD payment, bank, stablecoin, actual deposit, purchase, sale, exchange, withdrawal, payout, card, blockchain, stable-value guarantee, investment, yield, or money-transfer functionality.
2. No actual member-wallet binding, identity verification, authorization, custody or persistent transactions.
3. No API, server-side writing, D1 migrations, new Cloudflare binding, worker route, secrets or backend deployment.
4. No financial permissions or transfers in RHEN, Alpaca, Chime or any third-party service.
5. No implemented post-quantum signatures, cryptographic audit authentication, private keys, key recovery or financial-grade integrity controls. Those require a separate threat model, implementation and third-party verification.
6. No automatic public navigation exposure. The member-overview link is additive; direct route access is allowed only for the unconnected fictional demo when separately deployed.
